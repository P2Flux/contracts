# P2Flux contracts v2: internal adversarial review, 2026-11-24

**This is an internal review by a reviewer who did not write the code. It is not an audit and gives
no guarantee.** "Nothing found" means the attacks below were tried and failed. It does not mean the
code is secure.

## 1. Scope and method

- Branch `feat/contracts-v2` at `034e379` (local). Files: `contracts/v2/*.sol`: `P2FluxFeeRegistry`,

## 5. Findings, ranked

No critical, high or medium finding. Every PoC is in `test/foundry/v2/review/ReviewFindings.t.sol`
unless a fork test is named.

### R-01 (Low): a direct payment to the contract itself locks the funds forever
`P2FluxSend.send(to = address(sender))`, `P2FluxSplitterV2.pay(recipient = address(splitter))`, and a
recurring authorization with `recipient = address(recurring)` all succeed. No function can ever move
those funds out. The relayed paths are protected by the residual-balance check (control test).
- **Impact:** the sender loses the full amount (PoC: 100 USDC; recurring loses 9.80 USDC per period).
  Only through user or integration error. No attacker gain.
- **PoC:** `test_R01_sendToSendContractLocksFunds`, `test_R01_payToSplitterLocksFunds`,
  `test_R01_recurringToItselfLocksFundsEveryPeriod`, `test_R01_control_relayedPathsRefuseSelf`.
- **Fix:** in `send`, `pay` and `charge`, add
  `if (to == address(this)) revert ZeroAddress();` (or a new `InvalidRecipient`). The API should also
  refuse its own contract addresses as recipients.

### R-02 (Low): payment contracts trust the registry's numbers without re-checking the caps
`_fees()` uses whatever `feeFor` returns. The constructor checks only that the registry address has
code. A wrong registry address in a manifest, or a future registry with a bug, could take 100% of a
payment. `minimumAmount` divides by zero at 10,000 bps.
- **Impact:** with a rogue registry, the merchant gets 0 of a 100 USDC payment (Splitter), or 1 base
  unit (Sponsored, through the fixed fee). This is a deployment-time trust issue only; there is no
  runtime attacker.
- **PoC:** `test_R02_rogueRegistryTakesWholePayment`.
- **Fix (2 lines in `P2FluxV2Base._fees`):**
  `if (bps > 200 || fixedFee > 0.2e6) revert RateAboveCap();` (constants mirrored from the
  registry). Also check `registry.MAX_BPS() == 200` in the constructor. The caps then hold even if the
  registry is wrong.

### R-03 (Low): a legal fee increase permanently bricks small existing subscriptions, and `isChargeable` hides it
A subscription is signed once for a fixed `amount`. If the fixed fee or the rate rises within the caps
so that `amount <= fee + fixed`, every later `charge` reverts `AmountTooSmall`, while `isChargeable`
still returns true.
- **Impact:** the merchant loses that subscription's revenue until the payer re-signs. Only small
  subscriptions are affected: today a 0.15 USDC/month subscription is fine, but at a fixed fee of 0.20
  any subscription ≤ ~0.204 USDC dies. It also misleads the relayer's scheduler (wasted gas on
  reverts).
- **PoC:** `test_R03_feeIncreaseBricksSmallSubscription`.
- **Fix:** add the `amount > fee + fixed` check to `isChargeable`. Off chain, enforce a subscription
  minimum that survives the caps: `amount > 0.20 / 0.98`, about 0.21 USDC, or simply ≥ 1 USDC.

### R-04 (Informational, owner decision): the recurring fixed fee is charged even when the relayer did not pay the gas
`charge` is public. When the payer, the merchant or anyone else executes it, the reimbursement is
correctly 0, but the 0.05 fixed fee still goes to the gas treasury. The owner rule says the fixed fee
is "never when the buyer pays their own gas".
- **Impact:** 0.05 USDC per self-executed charge, paid by the merchant.
- **PoC:** `test_R04_fixedFeeChargedWhenPayerPaysOwnGas`.
- **Fix or decision:** either accept it (subscriptions are a relayed product, as in v1), or charge
  `fixedFee` only when `msg.sender == relayer`. Note the trade-off: merchants could then self-execute
  to skip the 0.05.

### R-05 (Informational): anyone chooses when a due rate change applies, anywhere in a 7-day window
`executeRate` is permissionless. Between ETA and ETA + 7 d, the new rate starts whenever any address
chooses. Every relayed send already signed at the old rate then fails the token's signature check.
- **Impact:** denial of service on in-flight relayed sends only (the sender re-signs). Merchants also
  cannot know the exact moment a change takes effect. No funds at risk.
- **PoC:** `test_R05_strangerExecutesRateAndKillsInFlightSends`. On real USDC:
  `test_fork_relayedSendAndRateChange`.
- **Fix:** have the API/ops call `executeRate` exactly at ETA, and stop quoting old rates shortly
  before ETA. Simpler option: lazy activation. `feeFor` returns the pending rate once
  `block.timestamp >= eta`, which removes `executeRate` and makes the effective time exact.

### R-06 (Informational): the same order can be settled once per contract
The v2 Splitter, v2 Sponsored (and both v1 contracts) compute the same `paymentId`, but each keeps its
own replay table. The same `(recipient, amount, ref)` can be paid on each of them. This is the v1
design.
- **Impact:** a buyer can pay one order twice, for example a wallet retry on the direct path after a
  sponsored attempt. The refund is off chain.
- **PoC:** `test_R06_sameOrderPaidTwiceAcrossContracts`.
- **Fix:** the API must bind each intent to one contract, and check all four tables (v1 and v2)
  before showing a pay button or offering a refund.

### R-07 (Informational, business): a relayed Send is a cheaper, gasless, ref-tagged payment rail
A merchant can take payments as relayed sends (invoice number in `ref`, exact amount received). The
fee is 0.1% + 0.05, paid by the buyer, instead of 1% + 0.05 through the sponsored checkout.
- **Impact:** on a 100 USDC sale, P2Flux earns 0.15 instead of 1.05 USDC, and the merchant receives
  100.00 instead of 98.95.
- **PoC:** `test_R07_sendUndercutsSponsoredPayment`.
- **Fix:** this is a policy matter, enforced by the relayer. Rate-limit relayed sends, refuse sends
  to known merchant wallets, or price relayed sends above the one-time rate when `to` is a registered
  merchant. On chain the contract cannot tell the difference.
- **R-07b:** the rule "the API quotes zero extra gas" is not enforced on chain; a relayed send with
  `networkFee = 0.25` settles. The sender signs it, so this is not exploitable without consent. Deploy
  `P2FluxSend` with `MAX_NETWORK_FEE_HARD_CAP = 0` if the rule is final. PoC:
  `test_R07b_relayedSendAcceptsNetworkFee`.

### R-08 (Informational): recurring admin compromise swaps the relayer instantly (no timelock)
`setRelayer` takes effect in the same block. Registry changes, in contrast, wait 48 h. A new relayer
can attach `min(signed max, GAS_REIMBURSEMENT_HARD_CAP)` to every charge it wins.
- **Impact:** small. The money goes to the immutable `gasTreasury`, not to the attacker. Payers
  overpay P2Flux by up to 0.05 USDC per charge (the Base cap). The admin is immutable, so a lost
  admin key leaves the relayer fixed for good.
- **PoC:** `test_R08_compromisedRecurringAdminInstantRelayer`.
- **Fix:** accept (documented in design §6), or time-lock `setRelayer` the same way as the registry.
  Use a multisig either way.

### R-09 (Informational): `executePartners` is all-or-nothing
One stale, cancelled or never-scheduled address reverts the whole batch.
- **PoC:** `test_R09_executePartnersAllOrNothing`.
- **Fix:** ops note only (execute exactly the scheduled list), or skip entries that are not due.

### R-10 (Informational, known): a blacklisted gas treasury or fee wallet stops the paths that pay it
This was proven on real Base USDC. Once Circle blacklists `gasTreasury`, every sponsored payment and
relayed send reverts. Direct `pay` keeps working. Both addresses are immutable, so the only recovery
is a redeploy. Design §7 already states this.
- **PoC:** `test_fork_R10_blacklistedTreasuryBricksRelayedPaths` (fork) and the existing
  `test_blacklistedFeeWalletReverts`.
- **Fix:** accept, and use clean, separate wallets. Keep a redeploy runbook.

Related fork observation, no issue: when a merchant is blacklisted, the payment reverts and the
buyer's EIP-3009 authorization is not consumed. It stays redeemable by the relayer until
`validBefore`, for example right after an unblacklist (`test_fork_blacklistedRecipientAuthStaysLive`).
Keep `validBefore` short (the API uses minutes), so a stale authorization cannot settle much later.

### T-01 (test harness, not a contract bug): `SponsoredSplitterV2.t.sol::testFuzz_conservation` is flaky
In one default-profile run, the fuzzer picked `makeAddr("partner")` = `0x5B51…036e` as the
"non-partner" recipient. The contract correctly applied 0.75%, and the test expected 1%. The cause is
that `_cleanAddress` (in `Helpers.sol`) does not exclude `partner`.
- **Counterexample:** `args=[500, 633, 0x…194b, 0x5B51…036e, false]`.
- **Fix:** in the v2 tests, add `vm.assume(a != partner)` (or an equivalent exclusion in a v2-level
  `_cleanAddress`). The same pattern may affect the other v2 `testFuzz_conservation` tests.
  Production code is not affected.

**New timelock checks: no issue found**
- **Ghost model.** `invariant_RR_registryMatchesEventLogModel` uses an independent model: an event log
  ("the last schedule whose 48 h passed with no later schedule or cancel inside its window"). It
  shares no structure with the current / next / ETA slot. It covers random schedule and cancel for
  all three kinds and the partner flag, plus warps landing exactly on ETA and on ETA − 1. In the same
  block it checks `Send.quote` and `Sponsored.minimumAmount` against the model.
- **Cancel after effect** reverts `NothingPending`. A cancel at ETA − 1 keeps the previously effective
  value, never the value before it (`test_RR2_*`).
- **Overwrite while pending:** the first value never applies, and the second needs its own full 48 h.
  A schedule made after an effect first rolls the effective value into `current` (`test_RR3_*`).
- **Partners:** duplicate addresses in one batch, changing list → unlist while pending, and cancel
  after effect all behave correctly (`test_RR4_*`).
- **Same block, all contracts:** a rate change for all three kinds and a partner unlisting, scheduled
  in the same block, switch together in all four contracts, exactly at ETA and not at ETA − 1. This
  is checked with real `pay` and `charge` calls (`test_RR1_*`).

**New observations (informational, PoC in `ReviewReReview.t.sol`)**
- **N-01 (accepted trade-off, design §3.3):** anyone can front-run the relayer's charge each period.
  The 0.05 fixed fee is then skipped, and the relayer's own transaction reverts
  `AlreadyChargedThisPeriod`, wasting its gas. Impact: up to 0.05 USDC of revenue per charge, with
  the merchant paying the gas itself. Ops fix: the relayer simulates the charge (or reads
  `lastChargedPeriodPlusOne`) before sending. PoC: `test_N01_thirdPartyFrontRunsRelayerSkipsFixedFee`.
- **N-02:** `isChargeable` is a relayer view. For an amount between `fee` and `fee + fixed`, it
  returns false while a non-relayer can still charge (without the fixed fee). The scheduler should
  not read "false" as "dead". PoC: `test_N02_isChargeableIsRelayerView`.
- **N-03 (gas / comment):** `RateSlot` says "one storage slot", but solc lays it out in **3 slots**
  (each nested `Rate` struct starts a new slot; `eta` sits in slot 2). This is correct, but every
  payment pays two extra cold SLOADs (~4.2k gas). Flattening the fields
  `b, pb, f, nb, npb, nf, eta` gives exactly 256 bits = 1 slot. `PartnerSlot` is 1 slot as claimed.
  Evidence: `solc --storage-layout`.

## 9. Unified contract `P2FluxPaymentsV2` (commit `6144890`)

Internal review, not an audit. Production code was not changed. Tests are in
`test/foundry/v2/review/ReviewUnified.t.sol` (`test_U*` = observation PoC, `test_UC*` = checked, no
issue).

**Runs**
- Full v2 suite, default profile: 144/144 pass (10 fork tests skipped offline).
- Fork, once: 10/10 pass. This includes the builder's cross-entrance tests on real Base USDC (public
  RPC, local anvil, block 61552000).

**Goal reached on chain:** one set of order terms `(token, recipient, amount, ref)` settles at most
once across both entrances, in either order and in the same block. Evidence: the builder's
`PaymentsCrossEntrance.t.sol`, the fork tests `test_fork_selfPaidThenSponsoredReverts` and
`test_fork_sponsoredThenSelfPaidReverts`, and `test_UC01`.

### Findings

**U-01 (Medium for the API / indexer; the contract works as designed): `ref` is not unique on chain.**
Decision 1 keys an order by its full terms. So the same `ref` can settle again with another amount
or recipient, through either entrance and on v1, and every settlement emits an event carrying that
`ref`.
- A buyer can "pay" their own 100 USDC order with 1 base unit and get a valid `Paid(ref)` event
  (`test_U01_underpaymentWithOrderRefEmitsPaid`).
- A self-pay at 100 followed by a sponsored retry at a re-quoted 100.5 both settle
  (`test_U01b_sameRefDifferentAmountSettlesTwiceAcrossEntrances`).
- v1 and v2 each settle the same order once (`test_U01c_v1AndV2SameOrderBothSettle`).

**What the API must enforce:**
1. Store each order's exact `(recipient, amount, ref)` once. Never re-quote the amount under the
   same ref: a new price needs a new ref.
2. Mark an order paid only by `PaymentSettled(id)` where `id` equals the stored
   `paymentId(...)`, or by an event whose net + fees equal the stored amount. Never by `ref` alone.
3. Before offering any entrance (including "auto"), check `isPaymentProcessed` on v2 **and** on the
   v1 splitter and sponsored splitter.
4. Treat any other settlement carrying the ref as an unrelated payment and refund it manually.

**U-02 (Info): two event shapes.** Self-pay emits `Paid(ref, recipient, token, net, fee)`, which has
no payer field. Sponsored emits `SponsoredPaid(…payer…, networkFee, fixedNetworkFee)`. Both also emit
`PaymentSettled(id)`. The entrance can be told apart by event type, and fees are complete
(`net + fee [+ fixed] = amount`). The indexer must take the self-pay payer from the USDC `Transfer`
log. The shapes are kept identical to v1 for compatibility. Optional fix: add a `payer` field to
`Paid`, or one `Settled(id, ref, recipient, payer, net, fee, fixedFee, networkFee, sponsored)` event.
PoC: `test_U02_eventShapes`.

### Checked, no issue

| Attack | Result | Test |
|---|---|---|
